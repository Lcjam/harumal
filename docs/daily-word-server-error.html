오늘의 단어
서버 오류

화면 코드는 배포됐지만 그 코드가 기대하는 데이터베이스 변경이 적용되지 않아 발생한 코드–스키마 불일치 장애를 분석하고, 실행 경로 자체에서 재발하지 않도록 고친 기록입니다.

소스 수정 완료 영향: /daily, /practice 원인 유형: 배포·마이그레이션 운영 반영: 재배포 필요

한 문장 요약

새 혼자 하기 기능은 solo_plays와 solo_attempts 테이블을 필요로 하지만, 직접 실행 경로인 npm start가 마이그레이션을 건너뛰고 server/index.ts만 실행했습니다. 새 코드만 반영된 운영 서버에서는 해당 테이블을 쓰는 요청이 모두 500이 됐습니다.

선택한 해결책 서버 시작 전에 마이그레이션을 항상 실행한다.

npm start와 Docker 모두 같은 시작 스크립트를 거치도록 통일했습니다.

01 / EVIDENCE

어떻게 원인을 좁혔나

HTTP 500

운영 `/daily` 재현

Chrome에서 실제 화면을 열었을 때 “서버 오류가 발생했습니다”가 표시됐고, 쿠키가 없는 새 요청의 GET /api/daily도 500이었습니다. 기존 사용자 데이터 손상 문제를 제외했습니다.

HTTP 500

연습 모드도 같은 실패

POST /api/practice도 동일하게 실패했습니다. 둘의 공통점은 새로 추가된 solo 테이블을 사용한다는 점입니다.

HTTP 200

DB 연결 자체는 정상

GET /api/health는 200이었고 익명 세션 쿠키도 발급됐습니다. PostgreSQL 전체 장애나 네트워크 장애는 아니었습니다.

DEPLOY GAP

배포 경로 불일치 발견

Docker의 시작 명령은 마이그레이션을 실행하지만 기존 npm start는 서버만 실행했습니다. GitHub Actions의 실제 deploy 작업도 runner 대기 후 취소돼 자동 배포가 완료되지 않았습니다.

02 / ROOT CAUSE

실패가 만들어진 흐름

기능 코드 추가오늘의 단어와 연습 모드가 solo 테이블을 조회·삽입
Migration 003solo_plays, solo_attempts 정의
npm start마이그레이션 없이 Express/Next 서버만 시작
스키마 불일치실행 코드는 새 테이블을 기대하지만 운영 DB에는 미반영
API 500공통 오류 처리기가 내부 DB 오류를 서버 오류로 응답

암호화 키 손상은 이번 원인이 아닙니다. 해당 복구 로직은 기존 daily 행을 읽은 뒤에 동작합니다. 이번에는 새 세션의 daily와 practice가 함께 실패했으므로 그보다 앞선 공통 DB 스키마 경로가 원인입니다.

03 / FIX

적용한 수정

PACKAGE START

시작 진입점 통일

npm start가 server/index.ts를 직접 실행하지 않고 scripts/start.ts를 실행하도록 변경했습니다. 이 스크립트는 마이그레이션 성공 후에만 서버를 띄웁니다.

DATABASE URL

두 실행 환경 모두 지원

일반 실행에서는 이미 설정된 DATABASE_URL을 보존하고, Docker에서는 기존처럼 APP_SECRET으로 최소 권한 앱 계정 접속 주소를 만듭니다.

FAIL FAST

마이그레이션 실패 시 서버 중단

스키마 변경이 실패하면 API 서버를 반쪽 상태로 열지 않습니다. 장애가 사용자 요청 시점의 모호한 500이 아니라 시작 로그의 명확한 실패로 드러납니다.

REGRESSION TEST

시작 계약 고정

시작 명령이 공통 스크립트를 사용하는지, 외부 DB URL 보존과 Docker용 URL 생성이 각각 유지되는지 자동 테스트를 추가했습니다.

04 / DECISION

가능한 해결책과 선택 이유

선택지 장점 단점 판단
시작 시 자동 마이그레이션 선택 모든 기동 경로가 같은 스키마를 보장합니다. 현재 단일 인스턴스 구조에서 운영이 단순하고, 누락된 Migration 003도 재배포만으로 적용됩니다. 시작 시간이 조금 늘고, 장시간 잠금을 잡는 대형 마이그레이션은 별도 운영 전략이 필요합니다. 현재 규모와 배포 방식에 가장 직접적이며 재발 방지 효과가 큽니다.
배포 전에 수동 실행 스키마 변경 시점과 앱 전환 시점을 운영자가 세밀하게 제어할 수 있습니다. 명령 한 번을 빠뜨리면 이번과 같은 장애가 그대로 반복됩니다. 실행 경로가 둘로 나뉩니다. 규모가 커져 별도 DBA 절차가 필요할 때는 적합하지만 현재 장애 원인을 제거하지 못합니다.
API 요청 중 테이블 생성 요청 시 즉시 자가 복구하는 것처럼 보입니다. 요청 경로에서 DDL이 실행되고 동시성·권한·지연 문제가 생기며 배포 문제를 숨깁니다. 사용자 요청과 스키마 관리를 섞으므로 제외했습니다.
오류 메시지만 개선 진단은 쉬워지고 사용자에게 일시 장애임을 더 잘 안내할 수 있습니다. 기능은 계속 고장 난 상태이고 DB 내부 정보 노출 위험도 관리해야 합니다. 관측성 보완책일 뿐 근본 해결책이 아니므로 단독 선택하지 않았습니다.

05 / VERIFICATION

수정 확인 결과

  • 빈 DB 기동npm start가 Migration 001~005를 순서대로 자동 적용했습니다.
  • 오늘의 단어 200새 서버의 GET /api/daily가 활성 daily 문제와 통계를 정상 반환했습니다.
  • 정답 비공개 유지진행 중 응답에 answer 필드가 없음을 함께 확인했습니다.
  • 단위 테스트시작 경로 회귀 테스트를 포함한 전체 테스트가 통과했습니다.
  • 통합 테스트daily 생성·통계·암호화 키 복구를 포함한 PostgreSQL 테스트가 통과했습니다.
  • 정적 검증TypeScript 타입 검사와 프로덕션 빌드를 검증 대상으로 포함했습니다.

운영 반영 시점: 이 수정이 Oracle Cloud에 재배포되어 새 시작 스크립트가 한 번 실행되면 누락된 스키마가 적용됩니다. 배포 전까지 현재 운영 URL의 500은 그대로일 수 있습니다.

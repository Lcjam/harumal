Incident review · 2026-08-23

오늘의 단어
서버 오류

운영 데이터베이스에 폐기된 hint NOT NULL 열이 남아 현재 코드의 INSERT를 거부한 레거시 스키마 장애를 분석하고, 전진 마이그레이션으로 바로잡은 기록입니다.

소스 수정 완료 영향: /daily, /practice 원인 유형: 변경된 과거 마이그레이션 운영 반영: 006 재배포 필요

한 문장 요약

운영 DB가 처음 적용한 003_solo_play.sql에는 solo_plays.hint가 NOT NULL로 있었습니다. 이후 같은 003 파일에서 열을 지웠지만, 적용 완료된 파일명은 다시 실행되지 않았습니다. 힌트를 보내지 않는 현재 INSERT가 제약 위반으로 모두 500이 됐습니다.

선택한 해결책 새 Migration 006에서 레거시 hint 열을 제거한다.

이미 배포된 마이그레이션은 고쳐 쓰지 않고 새 전진 마이그레이션으로 운영 스키마를 현재 정의와 맞춥니다.

01 / EVIDENCE

어떻게 원인을 좁혔나

HTTP 500

운영 `/daily` 재현

Chrome에서 실제 화면을 열었을 때 “서버 오류가 발생했습니다”가 표시됐고, 쿠키가 없는 새 요청의 GET /api/daily도 500이었습니다. 기존 사용자 데이터 손상 문제를 제외했습니다.

HTTP 500

연습 모드도 같은 실패

POST /api/practice도 동일하게 실패했습니다. 둘의 공통점은 새로 추가된 solo 테이블을 사용한다는 점입니다.

HTTP 200

DB 연결 자체는 정상

GET /api/health는 200이었고 익명 세션 쿠키도 발급됐습니다. PostgreSQL 전체 장애나 네트워크 장애는 아니었습니다.

DB CONSTRAINT

운영 로그로 직접 원인 확정

재배포 직후 앱 로그에서 null value in column "hint" of relation "solo_plays" violates not-null constraint를 확인했습니다. 운영 DB에도 003은 적용 완료였지만 레거시 열이 남아 있었습니다.

02 / ROOT CAUSE

실패가 만들어진 흐름

초기 Migration 003운영 DB에 solo_plays.hint NOT NULL 생성
003 파일 수정코드 저장소에서는 같은 파일의 hint 정의를 제거
재실행 안 됨schema_migrations가 파일명을 이미 적용 완료로 판단
INSERT 충돌현재 코드는 폐기된 hint 값을 보내지 않음
API 500PostgreSQL NOT NULL 위반으로 daily와 practice 모두 실패

처음 추정한 “마이그레이션 미실행”은 직접 원인이 아니었습니다. 운영 DB에는 003이 2026-08-15에 적용돼 있고 solo 테이블과 권한도 정상입니다. 문제는 적용된 과거 003의 실제 구조와 나중에 수정된 같은 파일의 내용이 달랐다는 점입니다.

03 / FIX

적용한 수정

MIGRATION 006

레거시 열 제거

ALTER TABLE solo_plays DROP COLUMN IF EXISTS hint를 새 파일로 추가했습니다. 운영 DB에 남은 정확한 열만 제거하고 빈 DB에도 안전하게 적용됩니다.

REGRESSION TEST

운영 스키마 계약 검사

통합 테스트가 information_schema.columns를 조회해 solo_plays.hint가 남아 있지 않음을 확인하도록 추가했습니다.

STARTUP HARDENING

시작 진입점도 함께 통일

이번 직접 원인과 별개로 npm start도 Docker처럼 마이그레이션 성공 후 서버를 띄우게 해, 수동 실행에서 신규 마이그레이션을 빠뜨릴 가능성을 없앴습니다.

RECOVERABILITY

변경 전 운영 백업

열 제거 전에 운영 PostgreSQL 전체를 백업하고 gzip 무결성 검사를 통과시켰습니다. 필요하면 변경 전 스키마와 2개의 기존 hint 값을 복구할 수 있습니다.

04 / DECISION

가능한 해결책과 선택 이유

선택지 장점 단점 판단
새 006에서 hint 열 제거 선택 현재 코드와 신규 DB 스키마에 정확히 맞고, 죽은 데이터와 제약을 함께 없앱니다. 기존·신규 환경 모두 IF EXISTS로 안전합니다. 기존 2개 행의 사용하지 않는 hint 값은 삭제됩니다. 복구하려면 배포 전 백업이 필요합니다. 제품에서 힌트를 완전히 폐기했으므로 가장 단순하고 일관된 최종 상태입니다.
hint의 NOT NULL만 해제 기존 hint 값과 열을 보존하면서 INSERT 오류를 빠르게 막을 수 있습니다. 코드가 사용하지 않는 열과 과거·신규 DB 차이가 계속 남아 다음 유지보수 때 혼란을 줍니다. 임시 호환 조치로는 가능하지만 최종 스키마로 부적합합니다.
INSERT에 빈 hint 추가 DB 변경 없이 구버전 스키마에서 즉시 동작합니다. 신규 DB에는 존재하지 않는 열이라 코드가 양쪽 스키마를 조건 분기해야 하고 폐기 기능이 되살아납니다. 스키마 부채를 애플리케이션 코드로 전가하므로 제외했습니다.
운영 DB에 수동 ALTER만 실행 가장 빨리 현재 서버 한 대를 복구할 수 있습니다. 코드에 변경 이력이 남지 않아 백업 복구나 새 환경에서 같은 문제가 반복될 수 있습니다. 즉시 복구만 되고 재현 가능한 배포가 아니므로 새 마이그레이션을 선택했습니다.

05 / VERIFICATION

수정 확인 결과

  • Migration 006로컬 DB에서 006이 적용되고 레거시 열이 없어졌음을 확인했습니다.
  • 스키마 회귀 검사통합 테스트가 solo_plays에 hint 열이 없다는 계약을 검증합니다.
  • 정답 비공개 유지진행 중 응답에 answer 필드가 없음을 함께 확인했습니다.
  • 단위 테스트시작 경로 회귀 테스트를 포함한 전체 테스트가 통과했습니다.
  • 통합 테스트daily 생성·통계·암호화 키 복구·스키마 검사를 포함한 PostgreSQL 테스트가 통과했습니다.
  • 정적 검증TypeScript 타입 검사와 프로덕션 빌드를 검증 대상으로 포함했습니다.

운영 반영 시점: Oracle Cloud에 새 006 파일을 전송하고 Docker 앱을 재배포하면 시작 단계에서 전진 마이그레이션이 한 번 적용됩니다. 적용 뒤 실제 daily·practice API를 새 쿠키로 다시 확인합니다.
